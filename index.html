Les VPN — Tunnel Serveur à Serveur

Dernière mise à jour : 18/12/2025

Définition & enjeux

Un VPN (Virtual Private Network) serveur à serveur, appelé également VPN site à site, est un tunnel chiffré établi de façon permanente entre les passerelles réseau de deux sites distants. Contrairement au VPN client-serveur (road warrior), il est totalement transparent pour les utilisateurs finaux : le trafic inter-sites circule comme s'il était sur le même LAN, sans aucune action de leur part.

L'enjeu principal est de garantir la confidentialité, l'intégrité et la disponibilité des échanges entre sites, tout en maîtrisant les coûts (pas de ligne dédiée MPLS nécessaire si Internet suffit).

Architecture & fonctionnement technique

Le tunnel est négocié entre deux équipements de bordure (routeurs, pare-feux, serveurs Linux avec WireGuard/OpenVPN). La mise en place se déroule en deux phases pour IPsec :

  • Phase 1 (IKE) — Authentification mutuelle des deux extrémités et négociation d'une clé de session via Diffie-Hellman. Le résultat est une SA (Security Association) IKE.
  • Phase 2 (IPsec) — Création des SA IPsec qui définissent les algorithmes de chiffrement (AES-256) et d'intégrité (SHA-256) appliqués aux données. Les paquets IP sont encapsulés en mode tunnel (nouvel en-tête IP) ou transport.

Avec WireGuard, la philosophie est radicalement différente : chaque pair possède une paire de clés Curve25519. Le handshake (Noise Protocol Framework) est ultra-rapide et la reprise de session après coupure est quasi instantanée. Le code source (~4 000 lignes) est environ 70× plus petit qu'OpenVPN, réduisant drastiquement la surface d'attaque.

Protocoles comparés

  • IPsec/IKEv2 — Standard industriel, natif sur Cisco/Fortinet/pfSense. Très interopérable, mais configuration complexe. Recommandé pour les liaisons entreprise-entreprise.
  • OpenVPN — Basé sur TLS 1.3, tourne sur UDP 1194 ou TCP 443 (utile en environnement filtré). Logiciel libre, très stable, multi-plateforme.
  • WireGuard — UDP uniquement, chiffrement moderne (ChaCha20-Poly1305), latence très basse. Intégré au noyau Linux depuis 5.6. Idéal pour les infrastructures modernes et les environnements Linux.
  • GRE + IPsec — Encapsulation GRE pour acheminer du routage dynamique (OSPF, BGP) dans le tunnel, chiffrement ajouté par IPsec.

Sécurité & bonnes pratiques

  • Utiliser des algorithmes robustes : AES-256-GCM, SHA-256 minimum, DH group 14+.
  • Rotation régulière des clés pré-partagées (PSK) ou utilisation de certificats PKI.
  • Surveiller les tunnels via SNMP ou Zabbix pour détecter les coupures.
  • Segmenter le trafic : limiter les flux autorisés à traverser le tunnel (ACL/firewall).
  • Journaliser et auditer les établissements/ruptures de tunnels.

Cas d'usage en entreprise

Connexion d'agences au siège social, accès sécurisé à un datacenter distant, liaison cloud hybride (on-premise ↔ AWS/Azure via VPN Gateway), ou interconnexion de zones réseau isolées dans une infrastructure industrielle (SCADA, IoT).

Mise en pratique — WireGuard sur Debian

# Installation
apt install wireguard
# Génération de clés
wg genkey | tee privatekey | wg pubkey > publickey
# Configuration /etc/wireguard/wg0.conf (serveur)
[Interface]
Address = 10.0.0.1/24
ListenPort = 51820
PrivateKey = <clé_privée>
[Peer]
PublicKey = <clé_publique_client>
AllowedIPs = 10.0.0.2/32, 192.168.2.0/24
# Démarrage
wg-quick up wg0

Protocole SNMP — Supervision réseau

Dernière mise à jour : 04/03/2026

Définition & rôle

Le Simple Network Management Protocol (SNMP) est un protocole applicatif standardisé (RFC 1157, 3411–3418) fonctionnant sur UDP, ports 161 (requêtes) et 162 (traps). Il permet la supervision, la collecte de métriques et la configuration à distance d'équipements hétérogènes : routeurs, switchs, serveurs, imprimantes, UPS, sondes environnementales, etc.

Architecture manager / agent

L'architecture SNMP repose sur trois composants fondamentaux :

  • Agent SNMP — Démon s'exécutant sur l'équipement supervisé (ex. : snmpd sur Linux). Il expose les données sous forme d'une arborescence d'objets : la MIB (Management Information Base).
  • Manager SNMP — Système de supervision centralisé (Zabbix, Nagios, PRTG, LibreNMS) qui envoie des requêtes GET/GETNEXT/GETBULK aux agents et traite les traps entrants.
  • MIB — Base de données hiérarchique (OID tree) décrivant chaque variable mesurable. Les OID standard (RFC 1213 — MIB-II) couvrent interfaces, IP, TCP. Les MIB propriétaires (Cisco, HP…) ajoutent des métriques spécifiques.

Types de messages

  • GET — Lecture d'un OID précis (ex. : charge CPU).
  • GETNEXT / GETBULK — Parcours ou récupération en masse de la MIB.
  • SET — Modification d'une variable (ex. : redémarrage d'une interface).
  • TRAP / INFORM — Notification proactive envoyée par l'agent au manager lors d'un événement (lien down, seuil dépassé). INFORM ajoute un accusé de réception.

Versions & sécurité

  • SNMPv1 — Authentification par community string en clair. À éviter en production.
  • SNMPv2c — GETBULK plus performant, toujours sans chiffrement. Encore très répandu sur du matériel ancien.
  • SNMPv3 — Apporte un modèle de sécurité complet : authentification (HMAC-MD5 ou HMAC-SHA), chiffrement du payload (DES ou AES-128/256) et contrôle d'accès (VACM). Seule version recommandée en production.

Mise en œuvre pratique

Dans un contexte SISR, SNMP est couplé à Zabbix pour la supervision d'infrastructure. Zabbix interroge les agents toutes les 30 s à 5 min, stocke les métriques dans MariaDB et déclenche des alertes (email, Slack) via des déclencheurs (triggers). Les données peuvent être visualisées dans Grafana via le plugin Zabbix-Grafana ou le connecteur native.

Configuration agent sur Debian

# Installation
apt install snmpd snmp
# /etc/snmp/snmpd.conf (SNMPv3)
createUser monUser SHA "motdepasse_auth" AES "motdepasse_chiffrement"
rouser monUser priv
agentaddress udp:161
view systemonly included .1.3.6.1.2.1
# Test depuis le manager
snmpwalk -v3 -l authPriv -u monUser -a SHA \
  -A "motdepasse_auth" -x AES \
  -X "motdepasse_chiffrement" 192.168.1.1 .1.3.6

OID courants à surveiller

  • .1.3.6.1.2.1.1.1.0 — sysDescr (description du système)
  • .1.3.6.1.2.1.2.2.1.8 — ifOperStatus (état des interfaces)
  • .1.3.6.1.2.1.25.3.3.1.2 — hrProcessorLoad (charge CPU)
  • .1.3.6.1.2.1.25.2.3.1.6 — hrStorageUsed (espace disque utilisé)

Décentralisation du stockage de données par la blockchain

Dernière mise à jour : 20/04/2026

Contexte & problématique

Le modèle de stockage de données dominant repose sur des silos centralisés : GAFAM, hébergeurs cloud (AWS S3, Azure Blob, Google Cloud Storage). Si ces services offrent disponibilité et facilité d'usage, ils soulèvent des questions fondamentales : qui détient réellement les données ? Qui peut y accéder ? Que se passe-t-il en cas de fermeture ou de décision unilatérale du prestataire ?

La blockchain et les technologies associées proposent une réponse par la décentralisation : distribuer le contrôle entre de nombreux nœuds indépendants, sans autorité centrale unique.

Fonctionnement de la blockchain

Une blockchain est un registre distribué immuable : chaque bloc contient un ensemble de transactions, un horodatage et l'empreinte cryptographique (hash SHA-256 ou Keccak-256) du bloc précédent. Modifier un bloc passé invaliderait tous les blocs suivants, ce qui est détecté immédiatement par le réseau.

  • Mécanisme de consensus — Les nœuds s'accordent sur l'état du registre via des algorithmes : Proof of Work (PoW, énergivore), Proof of Stake (PoS, plus économe), Delegated PoS, etc.
  • Contrats intelligents (Smart Contracts) — Programmes autonomes déployés sur la chaîne (Ethereum, Solana) qui s'exécutent automatiquement dès que des conditions prédéfinies sont remplies, sans intermédiaire.
  • Clés cryptographiques — Chaque participant possède une paire clé privée / clé publique. La clé privée signe les transactions ; la clé publique constitue l'adresse identifiable sur le réseau.

Stockage décentralisé — IPFS & Filecoin

Le stockage de fichiers directement sur une blockchain est prohibitif en coût et en taille. La solution retenue est hybride :

  • IPFS (InterPlanetary File System) — Protocole P2P d'adressage par contenu. Chaque fichier reçoit une empreinte unique (CID — Content Identifier). Le fichier est fragmenté en blocs répartis sur de multiples nœuds. Pour récupérer un fichier, on demande son CID au réseau : n'importe quel nœud qui le possède peut répondre. L'intégrité est garantie par le hash.
  • Filecoin — Couche incitative économique construite sur IPFS. Les fournisseurs de stockage sont rémunérés en FIL (jeton natif) pour héberger des données. Les contrats de stockage sont enregistrés sur la blockchain Filecoin, rendant les engagements vérifiables et transparents.
  • Arweave — Alternative orientée stockage permanent : un paiement unique couvre le stockage à perpétuité grâce à un fond de dotation algorithmique.

Souveraineté des données utilisateur

La décentralisation redonne aux utilisateurs le contrôle effectif de leurs données selon plusieurs axes :

  • Auto-hébergement sans tiers de confiance — Les données sont chiffrées côté client avant d'être stockées sur le réseau. Sans la clé privée de l'utilisateur, personne ne peut lire le contenu, pas même les opérateurs de nœuds.
  • Résistance à la censure — Un contenu publié sur IPFS ne peut pas être supprimé unilatéralement par un acteur central. Sa disponibilité dépend du nombre de nœuds qui l'épinglent (pin).
  • Portabilité & interopérabilité — Le CID d'un fichier est universel : il peut être référencé dans n'importe quelle application compatible IPFS, sans verrouillage propriétaire (vendor lock-in).
  • Traçabilité des accès — Les smart contracts permettent de définir des règles d'accès auditables : qui peut lire, modifier ou supprimer une donnée, avec une trace immuable de chaque autorisation accordée.

Limites & défis actuels

  • Persistance — Un fichier IPFS non épinglé peut disparaître si aucun nœud ne le conserve. Filecoin ou des services de pinning (Pinata, Web3.storage) compensent ce risque.
  • Confidentialité par défaut — IPFS est public ; le chiffrement des données avant publication est indispensable pour les usages sensibles.
  • Performance — La latence de récupération peut être élevée pour des fichiers peu populaires. Les accélérateurs comme les gateways HTTP (Cloudflare IPFS Gateway) pallient ce problème pour la consultation.
  • Régulation — Le cadre juridique (RGPD, droit à l'oubli) est difficilement conciliable avec l'immuabilité de la blockchain. Des solutions comme le chiffrement des données puis la destruction de la clé permettent une « suppression effective » sans altérer la chaîne.

Applications concrètes

Partage de documents médicaux inter-établissements, archivage d'actes notariaux, stockage de preuves judiciaires infalsifiables, diplômes vérifiables en ligne (EduCTX, MIT Digital Diplomas), gestion décentralisée d'identités numériques (DID — Decentralized Identifiers, W3C).
